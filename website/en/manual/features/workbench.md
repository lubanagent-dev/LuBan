# Developer Workbench

> This page covers the web console's admin pages and the end-user chat entry, login auth, the agent debug console, log diagnostics, user permissions, avatars, and a few session conventions relevant to debugging.

> Beginner path: to run the workbench for the first time, see [local run](/en/tutorial/01-setup-and-first-run).

The web console covers: agent definition editing and debugging (the debug console is a "conversation + prompt trial" dual-tab workbench), model comparison runs, prompt library management, Tool/MCP online testing, Skill management (upload/version/assign), knowledge management (upload/chunking/re-chunk/retrieval test, see [knowledge and memory](./knowledge-memory.md)), flow graphs (read-only topology of deterministic flows), Trace visualization, eval report viewing, log diagnostics, and user permission management. The frontend currently has 17 measured page routes; `/diagnostics` and `/security` are the platform troubleshooting and access-control entries, and `/chat` is the parallel end-user chat entry.

**Auth loop**: with the backend on `AUTH_ENABLED=true`, two login methods are supported: database accounts like `admin`, or continuing with an API key. Account tokens and API keys are kept only in the current page's memory — never in localStorage, URLs, or build artifacts; the account token takes precedence, and refreshing the page requires logging in again or re-providing the key. On login/logout/identity switch, the page clears the previous account's in-memory private data and query caches, then refetches under the new identity without reusing the old cache. REST, SSE streams, uploads/avatars share one identity source (`Authorization: Bearer <token-or-key>`); 401 responses are never auto-retried. `AUTH_ENABLED=false` is development mode: the backend admits an anonymous principal and the UI notes development mode; production must keep it `true`.

**Platform RBAC**: the `/security` page manages users, roles, and permissions. Built-in admin has all 10 permissions; operator covers config, runs, approvals, diagnostics, and evals; auditor is read-only but may view diagnostics; viewer is read-only without diagnostics. Menus and the `/diagnostics`, `/security` route guards only hide entry without permission; the backend still reloads user status and role grants on every `/v1` request and returns 403. Permissions are platform-level switches, not department, tenant, or row-level data isolation.

**Log diagnostics page (/diagnostics)**: two tabs, Runs and logs, each independently paginated (20 per page; paging issues real new requests, with `total` from the backend). The Runs tab filters by session, Run, Trace, user label, and status; the logs tab additionally supports request ID, time range, and keyword filters. The detail page shows the current Run, the execution tree (`runs[0]` is the real root), and descendant Trace events; correlated logs are server-paginated by root Run at 50 per page with `total` returned, so you can reach past the 500th entry. The `X-Request-ID` from responses can be pasted straight into the logs tab filter. The page shows `dropped_count` (cumulative dropped log entries across all causes: queue full, write failures, etc.) and `write_failures` (number of write/cleanup failure events, not entries). This is a read-only troubleshooting UI, not a log-collection configuration center.

**End-user chat entry (/chat)**: the sidebar's "End-user chat" opens a full-screen chat page without sidebar, aimed at end users — a top dropdown selects the agent (defaulting to the built-in customer service). When the agent allows an avatar, a companion column on the left shows it large (an icon fallback without one; 3D models are drag-rotatable, and if the model embeds speaking animation, the mouth animates during streamed replies and rests when done; auto-collapsed on narrow screens); after an agent turns display off, the chat page loads no avatar assets and the conversation area uses the freed width. Multi-turn conversations stream, tool calls show one status line (running/done/failed), and replies render as markdown on completion; the "New session" button switches sessions, and switching agents reopens automatically following that agent's display setting. Operations involving human confirmation (like large refunds) show "Approve / Reject" buttons inside the bubble; approval completes in-page and the conversation continues (the backend validates the `run:approve` permission and records the authenticated principal; only in development mode without auth does it fall back to the `decided_by` label). **Boundary**: this is a sample-level entry — no user registration / multi-tenancy / session-list persistence; requests reuse the workbench's in-memory account token or API key (not needed when `AUTH_ENABLED=false`); for production end users, build your own frontend and call LubanAgent over REST/SSE (integration notes in the [customization guide](../customization/overview.md)).

**Flow graphs page**: view the nodes and branch topology of registered deterministic flows (like the refund pipeline) — nodes colored by type (step / agent / human), conditional branches annotated with dashed double outgoing edges, and entry/sink marked with START / END. Read-only, reading the graph definition live without triggering compilation; **editing graphs happens in code** (`app/graphs/`; changing a flow = changing code and releasing, keeping flows testable and auditable); this page is not a visual designer. How to write graphs: [graph orchestration](./graphs.md).

**Prompt library page**: manages system prompts by prompt — list, create, edit and publish (new versions never overwrite old ones), version history, and assignment to agents (with reverse lookup of referencing agents). Assignment makes the target agent consume that prompt's current version: the system creates a new version of each assigned agent and resolves the prompt's full text into the snapshot (semantics in the [prompt library](./prompt-library.md)). The agent editor's instructions area is also dual-track: in reference state it shows a read-only prompt preview with a version badge and a one-click "convert to inline"; in inline state it can attach to a prompt reference.

**Model center page**: brain slots can be added; key/name/purpose edited; mappings changed; and slots deleted — including the four initial presets. The current environment comes from the server and model selection back-fills existing mappings; renaming keeps the old key as an alias and moves all environment mappings. The delete dialog lists every agent historical version's usage (primary slot, fallback slot, and summary dependency); with references, deletion is blocked, and the backend re-checks, using 409 as the concurrency backstop. The agent create/edit primary and fallback slots, plus model-comparison notes, all use the dynamic catalog, with old aliases still displayed. Viewing requires `config:read`, modifying requires `config:write`; details in the [model center](./models.md).

**Agent debug console**: entering an agent's debug console gives a "conversation + prompt trial" dual-tab workbench. The "Conversation" tab is multi-turn debugging around that agent; the "Prompt trial" tab runs two prompts of the same agent side by side — the library-defined baseline on the left, your modification on the right. Changing variables takes effect immediately; changing instructions is a temporary override (only this trial; not saved, not touching the agent definition). Trial content can be "loaded from the prompt library" and edited further. Switching tabs keeps state, and background streaming never breaks; conversation and trial sessions are independent.

**Avatar (agent editor "Identity" section)**: each agent can upload a display avatar — an SVG / PNG image or a GLB / GLTF 3D model (≤ 20 MB). The "Show avatar" switch defaults on; turning it off saves a new version, the chat page stops showing the avatar area, but the uploaded file and its name are kept, and you can re-enable anytime. Upload and removal take effect immediately and each generates a new version, without overwriting your unsaved display switch. Agents and versions without the field are treated as on. APIs: `POST /v1/agents/{key}/versions` (save the switch), `PUT /v1/agents/{key}/avatar` (multipart upload), `GET /v1/agents/{key}/avatar` (fetch the file), `DELETE` (remove). The avatar is presentation-only and never enters model logic; turning display off is neither deletion nor a permission restriction — logged-in users can still fetch the file via the API. Files are stored at `data/avatars/` (env `AVATAR_FILES_ROOT`).

A few session conventions relevant to debugging:
- **Conversation debugging (debug console "Conversation" tab)**: opening the page automatically starts a new session (new session ID) shared by the multi-turn conversation; refreshing the page starts a new session. If the agent has session memory, backend memory is read/written by this session ID, layering with the page's displayed history.
- **Prompt trial (debug console "Prompt trial" tab, side-by-side)**: every "run side-by-side" generates a new session ID, shared by both Runs (original / modified prompt) — findable as a pair in the Trace list, and avoiding the previous round's session memory polluting this comparison. The trial supports "load from prompt library": pick a prompt and its content fills the current editing-state trial (affects only this debug run, not the library prompt or the agent definition).
- **Trace list and detail**: each Run's session ID and user label are shown (— when absent), so "what happened for this user / this conversation" needs no database queries. What Trace records: [runtime observability](./observability.md).

**Language-switch boundary**: the workbench UI defaults to Simplified Chinese; the topbar and the `/chat` page can switch to English. The language preference lives only in the browser's localStorage and applies per browser, not per account. Switching translates static UI copy only — user input, prompt content, model replies, and API-returned data are always shown as-is, never translated; sample business fixtures and built-in prompts may be in Chinese, and image assets use the Chinese originals as source.
